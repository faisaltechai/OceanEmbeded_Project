# Live integrations layer — status and what to verify first

This document covers the layer added on top of the original synthetic-demo
OceanEmbed prototype: `backend/app/services/satellite/`, `services/gateway.py`,
`cache/`, `database/`, `scheduler/`, `reports/`, and the new
`/api/overview`, `/api/cyclones`, `/api/timeline`, `/api/report` endpoints.

## Why this document exists

This code was written in a sandboxed environment with **no outbound network
access and no ability to install FastAPI/httpx/SQLAlchemy/Redis/etc.**
Everything below was verified as thoroughly as that constraint allows; this
file tells you exactly which parts and what's left to confirm the first
time you run it somewhere with real internet and credentials.

## What was actually verified in the authoring sandbox

- **All backend Python files** pass `python -m py_compile` (no syntax errors).
- **The core "no fake data" contract** (`services/gateway.py`'s live → cache
  → demo fallback) was exercised with a mock live-source function and
  passed: a successful live call gets cached and returned as `status=live`;
  a subsequent failure correctly falls back to the *cached* value (not
  demo); a source with no cache and a failing live call correctly falls to
  `status=demo` with an explicit "no credentials configured" message.
  See `tests/test_regions_global.py`'s sibling assertions in this repo's
  history / conversation log for the exact test used.
- **The region bbox / "click anywhere on Earth" logic**
  (`core/regions_global.py`) is unit-tested in `tests/test_regions_global.py`
  and passes, including a regression test for a real bug this testing
  caught and fixed: a naive rectangular Pacific bbox originally swallowed
  the North American interior (Kansas resolved to "pacific_ocean"). Fixed
  with latitude-banded sub-boxes.
- **The PDF report generator** (`reports/generator.py`) was actually run,
  end-to-end, with representative data, and the output PDF was rasterized
  and visually reviewed — it renders correctly in the locked color palette.
- **The pre-existing ML core test suite** (`tests/test_ml_pipeline.py`,
  untouched by this work) still passes.
- **All three frontend HTML files'** inline JavaScript passes `node --check`
  (syntax-valid) and the HTML parses without errors.

## What was NOT verified (needs a real run to confirm)

- **Every live satellite client's actual HTTP behavior.** The code is
  written against each provider's current, documented API shape, but none
  of these calls were actually made:
  - NOAA CoastWatch ERDDAP / OSCAR currents (`satellite/erddap.py`) — public,
    no key needed, but verify the `dataset_id` constants
    (`jplMURSST41`, `jplOscar_U0.33deg`) still exist at
    `https://coastwatch.pfeg.noaa.gov/erddap/info/index.json` — NOAA
    renames/retires dataset IDs periodically.
  - Argovis (`satellite/argo.py`) — verify the current query parameter
    names and whether an API key is now mandatory (was optional as of
    authoring) at `https://argovis-api.colorado.edu/docs`.
  - NOAA NHC cyclones (`satellite/nhc_cyclones.py`) — verify
    `CurrentStorms.json`'s field names haven't changed.
  - Copernicus Marine (`satellite/copernicus.py`) — requires
    `pip install copernicusmarine xarray netCDF4` (commented out of
    `requirements.txt` as optional/heavy) and a free account; verify the
    dataset IDs against the current catalogue at
    `https://data.marine.copernicus.eu`.
  - NASA EarthData CMR search (`satellite/nasa_earthdata.py`) — the search
    API is public and stable, but granule download needs
    `EARTHDATA_BEARER_TOKEN`.
  - Copernicus CDS/ERA5 and CDSE/Sentinel-3
    (`satellite/era5_and_sentinel3.py`) — both need free-account credentials
    and were never exercised against the live services.
- **Redis.** `cache/redis_cache.py` was reviewed carefully but never run
  against a real Redis instance — only its in-memory fallback path is
  exercised by the gateway test above.
- **Postgres/PostGIS + Alembic.** The schema in
  `database/models.py`/`alembic/versions/0001_initial_schema.py` was
  hand-written to match, not autogenerated from a live database (no
  Postgres available to run `alembic revision --autogenerate` against).
  Run `alembic upgrade head` against a real Postgres+PostGIS instance and
  fix anything that doesn't apply cleanly.
- **The FastAPI app as a whole.** `app/main.py` was never actually started
  with `uvicorn` — only `py_compile`'d. The first `uvicorn app.main:app`
  run somewhere with `pip install -r requirements.txt` available is where
  import-order or dependency-version issues, if any, would surface.
- **All three frontend HTML files' fetch calls against a real backend** —
  the JS syntax is valid and the logic was carefully reviewed against the
  backend's actual response shapes, but no browser was available in the
  authoring sandbox to load these pages and click through them.

## Recommended first-run checklist

1. `cd backend && pip install -r requirements.txt && uvicorn app.main:app --reload`
   — fix any import errors first.
2. `curl localhost:8000/api/health` — confirm it starts and reports
   `cache_backend: "in-memory..."` (expected with no `REDIS_URL` set yet).
3. `curl localhost:8000/api/cyclones` and `curl localhost:8000/api/overview?region=bay_of_bengal`
   — these two use only key-free public sources (NOAA NHC, NOAA CoastWatch
   ERDDAP, Argovis) and are the best first real-network smoke test.
4. Open `frontend_src/oceanembed_demo.html` in a browser with the backend
   running on `localhost:8000` (or set `window.OCEANEMBED_API_BASE` in the
   page if serving from elsewhere) and confirm the backend-status badge
   goes green and the Overview page's live badges populate.
5. Only then work through the credentialed sources (Copernicus, NASA,
   CDS, CDSE) one at a time, following the `.env.example` comments.
